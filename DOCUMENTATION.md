# «Своё Вино»: документация решения

Версия документа: 29 сентября 2026 года. Репозиторий содержит мобильное веб-приложение, каталог российских вин, сервис визуального поиска и воспроизводимый контур оценки. Документ описывает поставляемую конфигурацию; экспериментальные и облегчённые режимы названы отдельно.

## 1. Назначение и состав

Пользователь снимает бутылку целиком или загружает готовую фотографию. Сервис возвращает наиболее похожее вино, альтернативы и карточку продукта. Для проверки по контракту задания предусмотрен отдельный endpoint, возвращающий только идентификатор `slug`. Приложение также содержит каталог с поиском и фильтрами, историю сканирований, карточки вин, аналоги и подбор вина к блюду.

Основной стек: Nuxt 4 и Nitro для веб-приложения, FastAPI для ML API, PyTorch/Transformers и SigLIP 2 для визуального поиска. Основной режим рассчитан на отдельный GPU-сервис. Односервисный dHash-режим без GPU сохраняется как ограниченный запасной вариант и не подменяет основную модель.

| Компонент | Поставляемый артефакт | Назначение |
| --- | --- | --- |
| Приложение | `frontend/` | Камера, загрузка фото, каталог, карточки, история и Nuxt API |
| Данные | `dataset/vino-svoe/`, `data/site_reference_review.tsv` | Снимок сайта, оригиналы и нормализованные фото, правила допуска эталонов |
| Модель | `ml/models/siglip2-site-label-adapter.safetensors` и JSON sidecar | Обученный адаптер к закреплённому базовому SigLIP 2 |
| ML-сервис | `ml/src/wine_cv/` | Проверка галереи, построение индекса, ранжирование и HTTP API |
| Оценка | `ml/reports/runpod-2026-09-29/`, `eval/` | Воспроизводимые внутренние результаты и контракт приёмочного прогона |

Базовые веса `google/siglip2-base-patch16-384` не дублируются в Git: первая подготовка скачивает публичный checkpoint строго по ревизии `f775b65a79762255128c981547af89addcfe0f88`. После построения автономного релиза checkpoint включается в его локальный model cache.

## 2. Схема обработки

```text
Снимок vino-svoe.ru + исходный CSV
  → проверка slug, связей с фото и SHA-256
  → эталонная галерея 1 936 вин
  → полная бутылка + деталь этикетки
  → SigLIP 2 + обученный адаптер → индекс эмбеддингов

Камера / загруженное полевое фото
  → ориентация EXIF, RGB и стандартный процессор SigLIP 2
  → эмбеддинг полного кадра → точное косинусное ранжирование
  → ML API → Nuxt API → карточка и Top-5
```

Набор эталонов мал для приближённого векторного индекса: поиск идёт по всем нормализованным векторам. Для каждого вина индексируются вид полной бутылки и кроп этикетки из пикселей исходного эталона. Полевой запрос остаётся полным кадром: проверенный в этой конфигурации автоматический детектор бутылки, OCR или удаление фона не заявлены. Это сохраняет информацию, когда бутылка смещена относительно центра и кроп ошибся бы.

## 3. Данные и нормализация

В исходном CSV — 4 147 записей и 2 103 уникальных `slug` после удаления 2 044 дублей. Снимок сайта содержит 2 110 карточек и по 2 110 исходных и нормализованных фотографий. К основному каталогу Nuxt добавлены 75 позиций сайта, которых нет в старом CSV: в приложении всего 2 178 карточек. Допущенная галерея содержит 1 936 эталонов; каждый её `slug` разрешается в продуктовый каталог.

Парсер берёт URL карточек и больших изображений из sitemap, а атрибуты вина — из серверного Nuxt payload страницы. Он сохраняет название, производителя, категорию, регион, цвет, сорт, крепость, описание, гастрономию и другие опубликованные поля без догадок о незаполненных значениях. Загрузка возобновляется после прерывания: уже сохранённые файлы проверяются по SHA-256. Точный `slug` служит ключом объединения с CSV; совпадение по похожему имени не считается доказательством идентичности вина.

Исходные изображения остаются неизменными. Производное эталонное изображение — детерминированный lossless WebP 768×768: учитывается EXIF, прозрачные поля обрезаются, пропорции бутылки сохраняются, фон заполняется белым. Непрозрачный фон не вырезается автоматически; изображение не растягивается и недостающие детали этикетки не «восстанавливаются». В карточках снимка сохранены URL, время загрузки, размеры, параметры нормализации и хеши оригинала и производной. Файл `data/site_reference_review.tsv` связывает ручное решение с SHA исходного фото: при смене фотографии старое разрешение не применяется молча.

Имя `gallery-reviewed-candidates.jsonl` означает применение правил ревью, а не ручную проверку каждой из 1 936 фотографий. В составе галереи 1 909 автоматически связанных изображений сайта, 11 явно допущенных после проверки спорных связей и 16 автоматически связанных legacy-эталонов. Неоднозначные, дублированные и конфликтующие изображения исключаются. Историческая strict-галерея на 928 вин оставлена только для сравнения и запасного dHash-индекса, а не как источник основного GPU-релиза.

Переносимая галерея лежит в `dataset/vino-svoe/gallery-reviewed-candidates.jsonl`; она не зависит от локального `work/`. Её целостность и соответствие адаптеру проверяет `make verify-production` по SHA файлов, уникальности `slug`, размеру и упорядоченному digest `(slug, image_sha256)`.

## 4. Модель и обучение

Визуальная основа — замороженный vision encoder `google/siglip2-base-patch16-384`. Поверх него обучен rank-64 residual adapter. Обучение на NVIDIA RTX 5090 выполнялось в FP16, batch size 32, 15 эпох, seed `20260929`, по четырём обучающим видам каждого эталона и одному отдельному proxy-виду для выбора эпохи. Полные бутылки и кропы этикеток подвергались ограниченным изменениям масштаба, поворота, экспозиции, контраста, насыщенности, размытия, блика и частичного перекрытия. Реальные полевые фотографии и закрытый тест в обучение не включались.

SHA-256 поставляемого адаптера: `bde343102f06d5e4fe02df953ecce622e2725deb800a0fa57eb34b99d3bf9701`. Рядом лежит sidecar с идентификатором модели, ревизией, digest галереи, гиперпараметрами, версиями runtime и историей эпох. Кэш эмбеддингов привязан к содержимому галереи, адаптеру, процессору, точности и версиям библиотек. Несовместимый кэш должен отвергаться или перестраиваться при подготовке, а не использоваться в инференсе.

Нормализованные эмбеддинги сравниваются по cosine similarity. Это относительный балл ранжирования, **не вероятность правильного ответа**. Без отдельно откалиброванных порогов продуктовый API возвращает `low_confidence`; значения порогов в `.env.example` намеренно пустые. Режимы `matched` и `not_found` нельзя считать статистически проверенными до отдельной разметки вин вне каталога.

## 5. Приложение и API

Камера показывает живой кадр; пользователь может свернуть видоискатель, переснять или выбрать файл. Перед отправкой браузер учитывает ориентацию, ограничивает длинную сторону 1 280 пикселями и формирует JPEG с качеством 0,86. Рамка видоискателя не обрезает снимок: в модель поступает полный кадр. На телефоне доступ к камере требует HTTPS, поэтому при отсутствии разрешения или защищённого контекста остаётся загрузка файла.

Каталог построен на предварительно созданном колонном индексе и виртуализированном списке. Поиск, фильтры, карточки, история, аналоги и подбор вина работают в том же Nuxt-приложении. 75 дополнительных site-only карточек имеют локальные изображения и те же `slug`, что и ML-галерея. При неразрешённом `slug` сервер не должен подставлять похожее вино под видом точного совпадения.

| HTTP маршрут | Назначение |
| --- | --- |
| `POST /api/v1/recognize` | Продуктовый ответ: `status`, `top1`, `top5`, карточка, время и метаданные модели |
| `POST /api/v1/eval/predict` | Контракт оценки: multipart-поле `image`, ответ `{"slug":"..."}` |
| `GET /api/v1/metadata` | Идентичность модели и состояние калибровки |
| `GET /api/health` | Проверка Nuxt |
| `GET /health/live`, `GET /health/ready` | Проверки внутреннего ML-сервиса |

ML API принимает JPEG, PNG, WebP и JFIF с поддерживаемым расширением имени файла, до 12 МиБ. Обращение к модели сериализовано внутри одного процесса; загрузка модели и проверка эталонов выполняются до состояния `ready`. Оценочный endpoint не использует фиктивный demo-ответ. При явно включённом `NUXT_ML_FALLBACK=dhash` он, однако, использует базовый dHash, поэтому перед оценкой SigLIP эту переменную необходимо очистить и проверить `/api/v1/metadata`.

## 6. Метрики и границы результата

Разметка включает 100 реальных фото: 64 подтверждённых точных SKU, 35 `not_in_catalog`, одно `uncertain`. Пять подтверждённых SKU отсутствуют в галерее; измерение поиска выполнено на 59 покрытых фото. Это однопроходный development pool, не независимый замороженный тест: шесть ответов требуют повторного ревью. Результат на официальном закрытом тесте отсутствует.

| Внутренний pool, 59 покрытых фото | Frozen SigLIP 2 | SigLIP 2 + адаптер |
| --- | ---: | ---: |
| Top-1 accuracy = micro-F1@1 | 39/59 (66,10%) | 41/59 (69,49%) |
| Recall@5 | 51/59 (86,44%) | 53/59 (89,83%) |
| Средний set-F1@5 | 28,81% | 29,94% |
| Recall@20 | 55/59 (93,22%) | 55/59 (93,22%) |
| Среднее время поиска, RTX 5090 | 199,66 мс | 200,84 мс |
| p50 / p95 поиска, RTX 5090 | 197,03 / 232,25 мс | 198,03 / 237,50 мс |
| Запросы быстрее 3 с | 59/59 | 59/59 |

При одном правильном `slug` на фото и одном обязательном первом ответе micro-F1@1 совпадает с Top-1 accuracy. Recall@5 — доля запросов, где правильный `slug` входит в первые пять. Для set-F1@5 предсказанием считается множество из `k≤5` кандидатов: значение равно `2/(k+1)` при попадании правильного вина и нулю иначе; при ровно пяти кандидатах максимум составляет 1/3. Recall@20 показывает потолок последующего reranking. p50/p95 — перцентили времени поиска внутри ML-сервиса после загрузки модели; HTTP, мобильная сеть и рендеринг интерфейса в это время не включены.

Адаптер дал +2 правильных Top-1 на этих 59 фото, то есть +3,39 процентного пункта. Малый pool и однопроходная разметка не позволяют утверждать, что прирост устойчив вне выборки. Даже на покрытой части **не достигнута цель ТЗ 90% Top-1**. Синтетический proxy обучения — проверка регрессии на производных каталога, а не оценка распознавания в магазине. Скорость и контракт следует дополнительно проверять на целевом сервере; полевой отказ для 35 вин вне каталога не откалиброван.

Подробный протокол, хеши галереи/запросов/ответов, версии runtime и построчные предсказания: [отчёт о точности](ml/docs/FIELD_ACCURACY_REPORT.md) и [машинные receipts](ml/reports/runpod-2026-09-29/).

## 7. Запуск и поставка

### Локальный полный стек

Требуются Python 3.10+, Node.js из `frontend/.nvmrc`, npm и доступ к публичному checkpoint при первой подготовке. Из корня репозитория:

```bash
nvm use
make local
```

Подготовка создаёт `.venv`, устанавливает зависимости, проверяет эталоны, строит индекс для текущей машины и собирает Nuxt. Она использует поставляемый адаптер **без переобучения**. Приложение открывается на `http://127.0.0.1:3000/scan`, ML API — на `http://127.0.0.1:8080`. `ML_DEVICE=auto` выбирает CUDA, Apple MPS или CPU. Скорости RTX 5090 нельзя переносить на CPU или Apple MPS.

### GPU-релиз

Для автономного GPU-развёртывания индекс необходимо строить в том же контейнерном runtime и с теми же настройками, что используются при инференсе. Кэш с macOS/CPU или от старой 928-SKU галереи нельзя переносить в GPU-контейнер. На NVIDIA-хосте подготовьте релиз штатным скриптом:

```bash
ml/scripts/build_gpu_release.sh
cp .env.example .env
docker compose up --build
```

Скрипт подготавливает базовый checkpoint и индекс для новой галереи в целевом ML-образе, проверяет их соответствие адаптеру и формирует `work/release/`. Внешний порт имеет только Nuxt; ML доступен внутри Docker-сети. Перед приёмкой проверьте `GET /api/v1/metadata`: ожидаются `pipeline=siglip2`, `gallerySize=1936`, закреплённая ревизия и SHA адаптера. `calibrated=false` корректно отражает отсутствие порогов отказа.

Отдельный Railway-образ на одном Nuxt-сервисе может работать без GPU при `NUXT_ML_FALLBACK=dhash` и `NUXT_PUBLIC_LITE_SCAN=true`. Он использует старый компактный индекс из 928 эталонов и помечен как «Базовый поиск». Его точность на полевых фото не измерена; это не эквивалент основной поставки.

## 8. Проверки и приёмка

После `make local` либо `make install` запустите из корня репозитория:

```bash
make release-check
```

Проверка включает Python-тесты, Nuxt lint/typecheck и тесты, production-сборку, HTTP smoke, проверку секретов и проверку SHA поставляемых эталонов/адаптера. Чистый checkout не должен зависеть от скрытых файлов `work/` для чтения каталога или сборки интерфейса. Состояние модели и источников фиксируется при создании релиза; изменение фото, галереи, preprocess или весов после открытия закрытого теста делает прежние метрики неприменимыми.

Три изображения в `eval/queries/` служат только для проверки формата ответа. После получения закрытого пакета организатора его следует положить в `eval/test/` без переименования и запустить `make october-test`. Скрипт проверяет пути и SHA входов, отправляет изображения по одному, сохраняет порядок запросов, ответы, latency и метаданные модели в игнорируемом `work/acceptance-<timestamp>/`. Без официальных правильных ответов этот прогон не вычисляет accuracy или F1. Протокол описан в [eval/README.md](eval/README.md).

## 9. Эксплуатационные ограничения

- Галерея ограничивает множество возможных ответов: отсутствующий SKU невозможно найти точным retrieval.
- Оптические блики, мелкий год, сильное перекрытие, несколько бутылок и необычный ракурс могут привести к ошибке; отдельные OCR и детектор бутылки в поставку не входят.
- Косинусный балл и разница Top-1/Top-2 не являются уверенностью модели. Пока пороги не откалиброваны на независимой выборке, UI не должен обещать достоверное совпадение или достоверное отсутствие вина.
- P95 из внутреннего GPU-бенчмарка не заменяет измерение полного HTTP-маршрута и мобильной сети на целевом хосте.
- Ручная разметка pool не прошла независимое второе ревью и группировку по физическим бутылкам. Она не заменяет закрытый тест.

Исходные фото хранятся в `dataset/`, ревью и ответы — в `data/`, а кэши, логи, сборки и закрытый пакет теста — только в игнорируемом `work/`. Сервис разметки `/annotate` предназначен для локальной или доверенной среды и по умолчанию недоступен в публичном production. Секреты и личные данные не входят в runtime-артефакты.
