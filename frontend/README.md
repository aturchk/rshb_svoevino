# Сканер вин «Своё Вино» — модуль каталога

Веб-модуль для платформы [«Своё Вино»](https://vino-svoe.ru). Mobile-first.
В production-режиме Nuxt проксирует фото во внутренний SigLIP 2 сервис; отдельно
есть явно помеченный demo-режим для UI-проверок без GPU.

Стек взят из рекомендованного в ТЗ кейса: **Nuxt 4**. Платформа заказчика работает
на нём же (проверено: `x-powered-by: Nuxt`), поэтому модуль можно встроить в их
приложение как есть, а серверный слой для скрипта оценки живёт в том же проекте.

## Запуск

Нужен Node **22.23+** (в проекте `.nvmrc`).

```bash
nvm use
npm ci
npm run build:images   # один раз: ресайз фотографий из ../dataset (~11 с)
npm run dev            # http://localhost:3000
```

Для полноценного UI-smoke без ML-сервиса:

```bash
NUXT_PUBLIC_DEMO_SCAN=true npm run dev
```

Готовые `public/data` и `public/img` закоммичены, поэтому после `npm ci` приложение
запускается сразу — `build:images` нужен только при обновлении датасета.

### Проверка с телефона

```bash
npm run dev:mobile     # https://<ваш-ip>:3000
```

HTTPS обязателен: `getUserMedia` работает только в защищённом контексте, и по
обычному http телефон камеру не даст никогда. Сертификат самоподписанный —
браузер один раз попросит подтвердить.

| Команда                               | Что делает                                         |
| ------------------------------------- | -------------------------------------------------- |
| `npm run dev` / `dev:mobile`          | дев-сервер, второй с HTTPS и доступом из сети      |
| `npm run build`                       | сборка датасета → сборка приложения                |
| `npm run build:data`                  | CSV → JSON, ~0.2 с                                 |
| `npm run build:images`                | ресайз фото с кэшем; `-- --force` пересобирает всё |
| `npm run lint` / `typecheck` / `test` | проверки                                           |

`NUXT_PUBLIC_MOCK_SCAN_HISTORY=true` включает демо-записи в истории сканирования
(по умолчанию раздел пуст — выдавать выдуманные сканы за настоящие нельзя).

## Экраны

`/` перенаправляет на `/scan`. Нижний таб-бар из трёх пунктов: **Каталог — Сканер —
История**, сканер приподнятым кругом в центре — самой досягаемой точке экрана для
большого пальца.

- **`/scan`** — живой видоискатель на 46% высоты экрана. Смахивание вверх сворачивает
  его, под ним открываются последние сканирования; смахивание вниз по полосе или
  кнопка «Сканировать» возвращают.
- **`/catalog`** — виртуализированный список 2103 вин, поиск, быстрые чипы,
  фильтры в нижней шторке (на десктопе — колонкой).
- **`/wine/:slug`** — карточка, рендерится на сервере: один запрос, без индекса.
- **`/history`** — история сканирования.

Титульного экрана нет намеренно: он дублировал обещание сканера, а его единственная
кнопка вела туда же, куда таб-бар.

## Архитектура

Feature-Sliced внутри `app/` (это `srcDir` Nuxt), зависимости строго вниз:

```
app (app.vue, layouts, assets) → pages → widgets → features → entities → shared
```

Проверяется ESLint-правилом `import/no-restricted-paths` с зонами: оно резолвит путь
и ловит в том числе `../../features/x`, тогда как `no-restricted-imports` смотрит
только на строку импорта. Скриптам сборки разрешён единственный слой — `shared`.

**Автоимпорт компонентов выключен намеренно.** Он делает связи между срезами
невидимыми, и проверять направление зависимостей становится нечего. Встроенные
композаблы Nuxt (`useState`, `useRoute`, `navigateTo`) автоимпортируются как обычно:
это API фреймворка, а не наши слои.

Контракт сгенерированных файлов — `app/shared/config/dataset-schema.ts`: его видит
и скрипт сборки, которому слой `entities` недоступен.

## Решения по производительности

**CSV не парсится в браузере.** Конвертация на сборке, RFC4180-парсером: в файле
6326 физических строк на 4147 записей — переводы строки живут внутри закавыченных
описаний, наивный `split('\n')` разваливается.

**Колоночный индекс** (structure of arrays). Выигрыш не в весе — gzip и так жмёт
повторяющиеся ключи — а в том, что при загрузке не аллоцируется 2103 объекта, а
фильтрация идёт по `Uint8Array`/`Uint16Array`/`Float32Array`. Датасет держится
в `shallowRef`: делать эти массивы глубоко реактивными — чистая трата на прокси.

**Файл на вино, а не шарды.** Детальная запись — 705 байт против 61 КБ у шарда из
88 позиций. Карточка денормализована, поэтому `/wine/:slug` — ровно один запрос.

**Инвертированные индексы** `Map<значение, Uint32Array>` строятся за один проход при
загрузке (~0.4 мс) и в JSON не хранятся: типизированных массивов там нет. Запрос —
гибрид: пересечение постинг-листов по категориальным фасетам, затем линейный проход
по кандидатам для подстроки и диапазона крепости.

**Счётчики фасет — динамические**, по схеме «без учёта собственного условия».
Статические врут, как только выбран любой фильтр; значения с нулём становятся
`disabled`, а не скрываются, иначе панель прыгает под пальцем.

**Web Worker не включён** — по правилу «если фильтрация превысит ~10 мс». Замер:
**0.344 мс** на 2103 позициях с пересчётом всех счётчиков.

**Три времени поиска разведены явно:** значение поля — локальное (0 мс); применение
фильтра — 0 мс; запись в URL — debounce 250 мс и всегда `replace`, иначе набор слова
«шардоне» кладёт в историю семь записей и «назад» перестаёт работать.

**Виртуализация** — `@tanstack/vue-virtual` по оконному скроллу. Высота строки
фиксирована (100/112 px), поэтому проход измерений не нужен. Ключ элемента — slug,
а не индекс массива. Позиция скролла восстанавливается при возврате с карточки,
но только если фильтры не изменились.

**Анимация видоискателя** — только `transform` и `opacity`. Панель это фиксированный
оверлей, место под неё резервирует распорка. В кадре 0 распорка схлопывается
(документ принимает финальную высоту) и тут же контенту выдаётся компенсирующий
`transform`; со следующего кадра включается transition. `transitionend`
фильтруется по `event.target` и `propertyName` — иначе переход фона у кнопки внутри
панели всплывает наверх и обрывает сворачивание на середине.

**Жест** — Pointer Events с `setPointerCapture`. Срабатывание по расстоянию
(30% высоты панели) ИЛИ по скорости (0.5 px/мс), но во втором случае обязательна
минимальная дистанция 24 px: без неё движение на 5 px за 10 мс сворачивает панель,
то есть любой быстрый тап со смазом. Мёртвая зона 8 px, осевая блокировка,
отсев старта на кнопках, `touch-action: pinch-zoom` на зоне жеста.

**Изображения** — `loading="lazy"`, реальные размеры каждого файла в индексе задают
точный `aspect-ratio`: нулевой CLS. Генерация кэшируется по
`sha1(путь + mtime + размер + параметры)` — повторный прогон меньше секунды вместо
107; `sharp` импортируется динамически и только когда есть работа.

**Размер клиента:** два основных чанка 33.9 и 33.2 КБ gzip, каталог с движком
фильтрации — отдельные 13.8 КБ.

## Что взято из данных, а чего в них нет

Девять колонок дампа заполнены на 100% (сорт — 99.9%), но заполненность ≠ пригодность.
Поля ниже выведены из названия, артикула и описания на этапе сборки
(`scripts/lib/derive.ts`, `grapes.ts`, `pairing-note.ts`):

| Поле                   | Покрытие   | Как получено                                                                                                 |
| ---------------------- | ---------- | ------------------------------------------------------------------------------------------------------------ |
| Сахар                  | 82.1%      | регексп по названию и slug, включая латиницу (Extra Brut, Semi-Sweet)                                        |
| **Крепость**           | **73.1%**  | хвост slug и имени фото: `…-krasnoe-suhoe-135` → 13.5%; диапазон `13-15` — не точное значение, не выводится  |
| Игристое               | 17.4%      | название, имя фото (Brut, Blanc de Blancs, Pet-Nat) + перляж, метод Шарма, ремюаж в описании                 |
| Креплёное              | 39 вин     | портвейн, мадера, херес, кагор, солера; сладкие от 15%                                                       |
| Канонический сорт      | 116 ключей | 140 строк сортов → синонимы сведены (Шираз = Сира), заглушки убраны                                          |
| Гастрономия винодельни | 9.1%       | дословная фраза из описания: «К красному мясу, выдержанным сырам»                                            |
| Выдержка в дубе        | 138 вин    | «дуб», «баррик» в описании; «бочки из акации» и «без выдержки в дубе» не считаются                           |
| Сладкое по описанию    | 7 вин      | сахар в названии не указан, но описание: «десертное вино», «вино позднего сбора» — только для правил сомелье |

Хвост крепости принимается, только если в строке есть маркер вина (цвет или сахар):
иначе `daniel-22` давал 22% (это год), а `Screenshot_19.webp` — 19%.
Канонические сорта нужны только машине — для похожих вин и правил сомелье; в карточке
и фильтре остаётся формулировка винодельни.

Крепость подтверждена двумя независимыми источниками: они совпали в 1534 случаях и
разошлись в нуле. Это единственное числовое поле каталога, на нём построен слайдер.

**Год** есть у 116 позиций из 2103 (5.5%) — ниже порога 30%, в UI не выводится.
**Цвет** заполнен на 100%, но это 826 свободнотекстовых значений; как фильтр
непригоден, поэтому идёт в карточку рядом с нормализованным семейством.
**Фотографии** резолвятся для 992 позиций (47.2%) — остальных файлов физически нет в
выданном пакете. Для них рисуется силуэт бутылки в цвете категории.
**Цен, рейтинга, отзывов, гастропар, объёма** в дампе нет вообще. Поэтому блок
«оценки» в карточке не рендерится — точка расширения описана в конце
`app/pages/wine/[slug].vue`.

## Швы под ML

**`app/entities/scan/api/recognizeWine.ts`** — клиентская сторона:

```ts
recognizeWine(image: Blob, signal?: AbortSignal): Promise<RecognizeResult>

interface RecognizeResult {
  status: 'matched' | 'low_confidence' | 'not_found'
  top1: RecognizeCandidate | null
  top5: RecognizeCandidate[]
  latencyMs: number
}
```

Сценарий «вина нет в каталоге» отличается от «нашли, но не уверены» — это требование
ТЗ, оцениваемое отдельно.

**`server/api/v1/eval/predict.post.ts`** — серверная сторона под скрипт оценки
кейсодержателя. Принимает `multipart/form-data` с полем `image`, проксирует запрос во
внутренний ML-сервис и возвращает плоский `{"slug":"..."}`. Demo-режим на этот endpoint
не влияет: acceptance test всегда проходит через настоящую модель.

## Тесты

`npm test` проверяет деривацию каталога, поиск, similarity, pairing и атомарное
сохранение ручной разметки. `npm run build` собирает production Nitro bundle, а
`frontend/scripts/smoke-demo.sh` поднимает его и проверяет страницы, health и полный
multipart scan-flow без GPU. Из корня всё запускается через `make test`.
